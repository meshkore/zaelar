# H001.4 — Hardening del self-update de Hermes

Revisión y endurecimiento del sistema H001 tras la restructura del repo (el feature migró de
`voice/brains/hermes/` + `assistant.html` (IIFE) a `brains/hermes/` + `frontend/app/components/UpdateBanner.js`).

## Qué se arregló / añadió

### 1. Bug bloqueante (crash al pulsar "Update now")
`brains/hermes/update_api.py` hacía `from . import active` — el módulo `active` vive en `server/active.py`,
así que el endpoint reventaba con `ImportError` en runtime (import lazy → `make test` no lo detectaba; el doc
H001.2 nunca ejecutó el `/update` de verdad). Corregido a `from server import active`.

### 2. Seguridad de upgrade — health-check ACP post-update
Tras `hermes update` con rc=0, "exit limpio" ≠ "sigue funcionando". Se añadió `_acp_healthcheck()`: levanta un
`HermesACP` real (`initialize` + `session/new`) y, si el binario nuevo rompe el contrato ACP, el SSE emite
`step: error` con la **versión previa** y la instrucción de rollback (`hermes update --version <prev>` /
`make install-hermes`) en vez de fallar mudo en el siguiente turno de voz. Protege conectores y features que
dependen del ACP.

### 3. Montaje brain-agnóstico (cerrar la fachada)
El feature estaba cableado a Hermes incondicionalmente. Ahora:
- `brains.active_brain()` decide qué se monta.
- `server/__init__.py` registra el router `/api/hermes/*` SOLO si `BRAIN=hermes` (import dentro de `create_app()`
  tras `load_into_env()`, para honrar el override del ⚙-panel).
- `GET /api/brain` expone el brain activo.
- `UpdateBanner.js` consulta `/api/brain` y aborta el polling si el brain no es `hermes`.

### 4. Paridad CLI (fuente única del comando)
`make update-hermes` (= `hermes update` + `hermes-check`) y `make hermes-check` (smoke-check ACP, mismo guard
que corre la UI). Ningún target `update-hermes` existía antes.

### 5. z-index del overlay
`.upd-ovl` 99999 → **100002**: por encima del orbo (100000) y del panel de settings (100001). Antes el orbo
flotaba sobre el overlay (el doc H001.3 lo describía al revés).
