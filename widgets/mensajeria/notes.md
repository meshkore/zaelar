# Messaging Widget: Context / Decisions (INI-015)

Single, first-class, hand-built widget (like `agenda`) that unifies the operator's personal messaging:
**WhatsApp + Telegram** today, with **email** as a future slot. Replaces the old `whatsapp` widget (deleted). It is
NOT generated by local Claude Code; its backend is the connector engines, not demand-generated code.

## Architecture Boundary
- **Engines**: `connectors/whatsapp/service.py` (vendored Baileys bridge) and `connectors/telegram/service.py`
  (Telethon userbot, in-process) run in the server lifespan (gated by `WA_ENABLED` / `TG_ENABLED`, always-on).
  **Both write the SAME store** `widgets/_data/mensajeria.json` through `connectors/messaging/store.py`
  (`platform="whatsapp"` / `"telegram"`).
- **Common layer** `connectors/messaging/`: `triage.py` (LOCAL platform-agnostic classifier), `store.py`
  (unified store), `notify.py` (proactive notice), `brief.py` (combined numbered brief), `dispatch_tag` (`[[msg.*]]`).
- **Widget**: `data.py` only reads the unified store through `messaging.store` and never raises. `widget.js`
  renders. The desktop auto-refreshes (`GET /widgets/mensajeria/data`), so live QRs and new messages appear by
  themselves.
- **Per-platform QR**: WhatsApp is generated by the bridge (data-URI PNG, ZAELAR-PATCH #3); Telegram is generated
  by the service with `segno` from the `tg://login` URL returned by `client.qr_login()`. Both travel through the
  store (`platforms.<p>.qr`), and the widget renders them as `<img>` in its connection card.

## Store Schema (`widgets/_data/mensajeria.json`, written by connectors)
`{platforms:{whatsapp:{status,qr},telegram:{status,qr}}, updated, items:[{n,platform,from,group,isGroup,body,urgencia,dirigido_a_mi,motivo,messageId,chatId,senderId}], pending_read:[{platform,chatId,messageId,senderId}]}`
- Per-platform `status`: off | no_creds | starting | connecting | connected.
- Actions (`apply_action`): `read` marks read in its app by enqueueing a key with `platform` in `pending_read`,
  drained by the correct connector; `dismiss` only hides; `clear` marks everything read.

## Decisions
- **Flat combined list by urgency**, not grouped by conversation or app; each row carries a platform badge
  (WhatsApp/Telegram/mail). `dirigido_a_mi` is highlighted in **yellow** (row `.me`, `--hb-warn-*`).
- When a platform is not linked (status connecting/no_creds/starting), show a **connection card with inline QR**.
  If the connector is `off` (disabled), omit it to avoid noise.
- Bodies are **untrusted**, so always use `textContent` (anti-XSS, widget-system invariant).
- Voice: `[[show:mensajeria]]` opens; `[[msg.read:N]]`/`[[msg.dismiss:N]]`/`[[msg.clear]]` control the combined
  list, routing the action to the correct connector based on `item.platform`.

## Redesign 2026-07-08: "simple" Profile by Default
- Operator: "a mess of text", too colorful; wants something like Apple Messages / Claude Code: vertical timeline,
  no per-message border, larger fonts, no duplicated title/channel, fewer icons and pills.
- **Two user-selected profiles, cosmetic only** (localStorage `hb-msg-profile`, never touches the store or Hermes):
  `simple` (new default, borderless timeline, `.tl`/`.trow`) and `completo` (the original design with cards and
  color badges, code intact in `richList()`). Both profiles render the same data; the profile only decides
  presentation.
- Header: title + one dot per platform (green `--hb-accent2` = connected, gray `--hb-neutral` = not connected) +
  gear icon opening/closing a Settings panel (profile + connected platforms + muted channels). The always-visible
  fixed footer with "connected/unlink" chips was replaced by this on-demand panel.
- Simple profile: platform badge = circle with initial (blue T, green W) instead of a pill with the name. Long
  messages (>220 chars or >4 lines) clamp to 3 lines (`-webkit-line-clamp`) with a "show more/less" link (state in
  `_expanded`, keyed by `messageId`). Body URLs are linked by `linkify()` building DOM nodes
  (textContent/createTextNode, never innerHTML; bodies remain untrusted). `cleanBody()` collapses 3+ consecutive
  line breaks to 2 without touching emojis/links.
- **Old bug fix**: `unhide` always sent `chatId:null`, so it never reactivated a muted channel (`data.py` requires
  `chat_id is not None`). It now sends `m.chatId` from `data.muted_channels`.
- **Visual bug fix**: when `from` and `group` match (typical Telegram channels like "Serenity Markets (News) ·
  Serenity Markets (News)"), the value is no longer duplicated; `group` renders only when different from `from`.
  Applies to both profiles.
- Explicitly rejected: amber/warning row background for "addressed to you" in the simple profile because it was too
  colorful. Replaced by a colored dot at the row's left edge (red=urgent, blue=for you).

## Adjustment 2026-07-08: Real Logos at the Top + Separate Title/Body
- Operator wants real WhatsApp/Telegram icons in the header, not just a color dot; confirms that the per-message
  badge with a T/W letter in blue/green is fine as-is. Also: visually differentiate the channel name (`from`) from
  the message's own "title", and that title from the rest of the body.
- **Logos**: official simple-icons.org outline (CC0), embedded as inline `<path>` (`BRAND_SVG`, `brandIcon()`), so
  it remains self-contained (no network/CDN at runtime; SVG lives inside `widget.js`). Colored with `currentColor`
  + `var(--hb-accent2)`/`var(--hb-accent)` (same tokens already used by chips), NOT real brand hex, to avoid adding
  a third palette. Header only; per-message badge remains a letter. Disconnected state = same icon dimmed through
  opacity, not a different gray, so the app remains recognizable. `.pdot`/`miniDot()` remains for the Settings
  panel connected list.
  **Parked idea**: if it ever pays off, `web/svg-brand-icons` can be re-audited against the source when
  `simple-icons` publishes a redesign. Frozen for now; do not auto-resync.
- **Title vs body** (`splitBody()`): many triaged messages arrive as `"Short title\n\nRest of text"` (for example,
  a weekly-vision heading followed by body text). When that pattern is detected (short line + blank line), the
  title renders semibold (`.ttitle`) and the rest in a more muted tone (`.tbody.sub`). If the message is a single
  block without that pattern, it renders as before. The 3-line clamp + "show more" now measures only the body; the
  title almost always fits on one line.

## Redesign 2026-07-08: Grouped by Chat + Open Thread Drill-in + Voice
- Operator: 30 loose messages in one day is too noisy; wants CHATS (one per conversation, with pending count) and
  to enter the full thread only when interested, by click or by voice ("show me the Telegram chat from X"). Also
  asked for a WIDE view (two columns, list + thread) "if it were wider".
- **Grouped (simple profile, list only): `_group_chats()` in `data.py`** groups the already-renumbered flat list by
  `(platform, chatId)`, preserving appearance order. There is no timestamp in the store, so the "last message" is
  the last by appearance order, not by clock. Each chat carries its own `n`, a separate addressing space from
  `items`, with urgency = the worst among its messages and `dirigido_a_mi` = whether any of them is addressed to me.
- **Open thread = server state, not client-only** (`db["active_chat"] = {platform,chatId}`,
  `widgets/mensajeria/data.py`): a widget click and a voice command (`[[msg.open:N]]`) converge in the same place.
  The widget never stores navigation state in JS; it always reads `data.active_chat` / `data.active_items` from
  `view_data()`. Auto-close when the thread runs out of messages, avoiding an empty thread waiting for "back" and
  avoiding resurrection if a new message arrives much later in that same chat after the operator considered it
  closed.
- **New tags** (`voice/tag_protocol.py` `MSG_RE`, generic dispatch unchanged; see
  `connectors/messaging/__init__.py::dispatch_tag`, which already routed any verb by `msg.` prefix):
  `[[msg.open:N]]` / `[[msg.close]]` (open/close a thread) and `[[msg.readchat:N]]` (mark a whole chat read without
  opening it). Available to both fast/duo layer and Hermes just like `msg.read/dismiss/clear`; they do NOT pass
  through the `"safe"` gate of `widget.data`, which is a separate mechanism only for `[[widget.data:ID]]` actions.
- **Double numbering, same pattern already used by read/dismiss**: without an open chat, N addresses the CHATS list
  (`msg.open`/`msg.readchat`); with an open chat, N addresses the MESSAGES list in that chat (`msg.read`/
  `msg.dismiss`), never both at once. `hide` (existing, through `[[widget.data:mensajeria]]`) inherits the same
  duality: without an open chat it interprets N as a chat; with an open chat, as a message. Same criterion, one
  place to remember it. `brief.py` changes its text depending on whether a chat is open, so the brain sees exactly
  the same numbering as the widget.
- **`brief.py` rewritten** to reflect grouped chats; previously it was a flat message list. It remains the only
  `[[msg.*]]` vocabulary source for the brain, injected through `brains/duo/prompt.py::_briefs()` every turn.
- Rejected as out of scope this time: real drag-resize of the widget. There is no resize mechanism in the canvas
  today, only move (`[[move:ID:where]]`); building it would be a `desktop.js` change for all widgets, not this one.
  The wide view (two columns) remains pending as a future cosmetic Settings toggle if needed. For now, simple
  profile = one column with "back"; complete profile remains intact.
- Complete profile (bordered cards) was NOT touched: it remains the original flat list, not grouped, no thread.
